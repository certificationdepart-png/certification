# Certification — безопасная отложенная отправка / security patch v2

**Статус:** исходники подготовлены локально; **production не изменён**. Ветка основана на присланном `certification-main.zip`; перед публикацией сравнить GitHub `main` и Vercel production SHA с этим архивом. Старый архив `certification-security-and-notifications.zip` НЕ использовать: он отменял отложенные сообщения полностью.

## 0. Факты из текущей диагностики

- В Supabase Data API выключен, приложение с прямым Prisma PostgreSQL подключением продолжает работать.
- Резервная копия `certification_20261029_113042.dump` создана пользователем и `pg_restore --list` её прочитал; полный restore-тест не делался. Не загружать дамп в публичные сервисы.
- `admin@example.com` уже имеет `role=user`, пароль credential=NULL и 0 сессий.
- Старые 412 событий `delayed_certificate_followup` переведены в `cancelled` и остаются в истории.
- Расширения `pg_cron`, `pg_net` установлены; пользователь проверил `cron.job`: нет заданий.
- **Рабочий старый Vercel deployment до замены продолжит создавать новые pending-события.** НЕ включать dispatcher до создания отсечки по дате активации.

## 1. В этом патче

1. Better Auth: `disableSignUp=true`, удалён автоподъём `role=admin`; публичная `/signup` перенаправляет на `/login`. Действующие администраторы не меняются.
2. Vercel build: удалён `db:seed`, чтобы тестовый `admin@example.com` не воссоздавался при deployment. Миграции оставлены — проверить их перед публикацией.
3. Удалён диагностический `/api/debug/auth-session`.
4. Старый `/api/cron/process-sync-jobs` **требует CRON_SECRET даже если env случайно пуст**; продолжает обрабатывать синхронизацию Google Sheets и события смены статуса, но **не отложенные сообщения**.
5. В новых событиях идентификатор детерминированный для пары application/course — повторное нажатие «Подтвердить» не создаёт второй follow-up.
6. **Система выключена по умолчанию**: `DELAYED_FOLLOWUPS_ENABLED=false`. Когда включена, новые задания создаются для включённых курсов с индивидуальным текстом и количеством дней.
7. Отдельный `POST /api/cron/process-delayed-messages` принимает только секрет `DELAYED_CRON_SECRET`; задачи выбираются только созданные после `DELAYED_FOLLOWUPS_START_AT`, уже наступившие по `nextAttemptAt`.
8. Атомарный захват PostgreSQL через `FOR UPDATE SKIP LOCKED`, максимум 5 сообщений за вызов; проверка текущего статуса заявки, соответствия чата и включения курса.
9. Telegram HTTP 429 → ограниченный повтор с задержкой, 4xx → `failed`; сетевые таймауты/5xx/неясный ответ → `needs_review`, **без автоматической повторной отправки**, чтобы снизить риск дублей. Зависшее `processing` также требует ручной проверки; автоматической переотправки нет. Telegram не предоставляет идемпотентного ключа для `sendMessage`, поэтому **абсолютную exactly-once гарантию получить нельзя**.
10. Успешная отправка отмечается `completed` до записи в `OutgoingMessageLog`: ошибка лога не инициирует повторную отправку.

## 2. Перед публикацией — контроль безопасности

- Сверить код с текущим GitHub/production (архив может отставать).
- Проверить действующий `CRON_SECRET` для старого Vercel cron; он обязателен для работы синхронизаций после правки.
- Вручную проверить права оставшихся 3 администраторов, рассмотреть отзыв ненужных сессий и ротацию секретов, проверить независимые API routes.
- Не включать обратно Supabase Data API. Права `anon` в БД по-прежнему широкие; проверить и сократить роли и grant отдельно, с планом отката.
- Проверить, что Vercel production **не запускает** старый build с `db:seed`.
- Не менять `AUTH_SECRET` и `DATA_ENCRYPTION_KEY` без отдельного плана — это может повлиять на сессии и расшифровку токенов.

## 3. Двухэтапное внедрение без массовой отправки

**Этап A — безопасный deploy с отключённой отправкой:**

1. В Vercel Environment Variables (Production) задать `DELAYED_FOLLOWUPS_ENABLED=false`; `DELAYED_FOLLOWUPS_START_AT` установить на будущую UTC дату (позже времени, когда старый deployment перестанет работать). Сгенерировать отдельный случайный 32+ символьный `DELAYED_CRON_SECRET` и сохранить только в Vercel, **без вставки в Git/чат**.
2. Опубликовать проект после review/CI, проверить работоспособность сайта, вход действующего admin, закрытие публичной регистрации (server-side), работу подтверждений и Google Sheets. Убедиться, что тестовый seed не запускался.
3. Проверить `ops/01_followup_preflight_READ_ONLY.sql`. Если старый deployment создал новые `pending` отложенные события, отменить только **явно выявленные legacy** после проверки, пока запуск dispatcher ещё отключён.
4. Создать в **Supabase Vault** секрет с именем `certification_delayed_cron_secret`, равный Vercel `DELAYED_CRON_SECRET`. Никаких значений в SQL-скриптах, коммитах и чатах.

**Этап B — включение только новых подтверждений:**

5. Зафиксировать точную UTC дату активации **после** остановки старого кода. Это значение должно отфильтровать все доактивационные события. Если время отложено в будущем, событие создастся только после наступления времени.
6. Изменить в Vercel `DELAYED_FOLLOWUPS_ENABLED=true`, проверить `DELAYED_FOLLOWUPS_START_AT` и провести production redeploy. Убедиться, что UI управляет задержкой по отдельным курсам.
7. Сначала test на тестовом чате / отдельной тестовой заявке, в идеале в отдельной тестовой БД. Убедиться, что новые event id имеют префикс `followup:` и старые 412 `cancelled`.
8. Только после проверок запустить `ops/02_activate_followup_cron_AFTER_DEPLOY.sql` в Supabase SQL Editor — создаётся `cron.schedule('*/5 * * * *')` c `pg_net.http_post` к защищённому маршруту. **Это единственный шаг, который начинает периодические HTTP-запросы.**
9. Мониторить `ops/04_followup_monitor_READ_ONLY.sql`, Vercel Runtime Logs фильтр пути, и ошибки `needs_review` / `processing` — не переотправлять их автоматически.

**Экстренная остановка:** `ops/03_stop_followup_cron.sql` — выключает планировщик; дополнительно `DELAYED_FOLLOWUPS_ENABLED=false` (потребует redeploy) прекращает создание/обработку новых заданий. В уже существующих заданиях история сохраняется.

## 4. Ограничения и тестирование

- Supabase `pg_cron + pg_net` вызывают HTTP маршрут как внешний клиент, а не через Vercel Cron; лимит частоты Vercel Hobby Cron **не применяется к расписанию Supabase**, но **использование Vercel Functions и Supabase лимитов тарифа сохраняется**.
- Погрешность доставки обычно несколько минут плюс API/network; точного SLA 24:00 гарантировать нельзя.
- Не забыть, что новый механизм сам по себе НЕ закрывает все риски системы: публичные PostgreSQL grants, возможные API authorization bypass, журналирование, и fallback для неопределённого статуса доставки требуют отдельного аудита.
- В этом окружении отсутствуют необходимые `node_modules`, а скачать их не удалось (нет доступа к npm registry), поэтому полноценные Vitest/TypeScript integration tests **не выполнены**. Запускать `bun install --frozen-lockfile`, `bun run typecheck`, `bun run test`, `bun prisma validate` и сборку в CI до production.
